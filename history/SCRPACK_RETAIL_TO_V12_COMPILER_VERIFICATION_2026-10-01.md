# BOTSD SCRPACK retail -> v1.2 compiler verification

Date: 2026-10-01

## Purpose

Close the remaining proof boundary for the v1.2 story localization build by running the maintained
translation-only source data against the exact retail `SCRPACK.SDA` and comparing the result to the
frozen public-v1.2 component.

## Structural discovery

The first retail golden run disproved the preparatory assumption that the count of parsed commands
inside each chunk remains fixed. Chunk 2 was eight bytes too large after text replacement.

Pairing the exact retail and v1.2 binaries established the actual rule:

- all 208 outer SDA chunk offsets are identical;
- all 184,683 meaningful command opcodes are identical by chunk/ordinal;
- the unused tail of each fixed chunk is repeated `opcode=0, payload_size=0` four-byte padding;
- translation growth consumes that padding and translation shrinkage creates more of it;
- 7,526 `0x1D03` dialogue commands and 262 `0x1F03` choice commands change payload size.

Five non-text command families contain command-relative u32 targets that the historical v1.2
compiler relocated after text resizing:

| Opcode | Target layout |
|---|---|
| `0x010C` | payload `+0x00`, one u32 target |
| `0x020C` | payload `+0x00`, one u32 target |
| `0x1212` | payload `+0x0C`, one u32 target; payload size 16 |
| `0x1312` | payload `+0x0C`, one u32 target; payload size 16 |
| `0x1412` | u16 count at payload `+0x06`, followed by that many u32 targets at `+0x08` |

For every one of these fields, the retail numeric target resolves to a retail command boundary and
the v1.2 value resolves to the same command ordinal after resizing. Across the exact pair:

- 1,960 commands contain at least one changed historical relocation field;
- 2,799 u32 target fields change value;
- zero changed relocation fields fail same-ordinal resolution.

The three `0x070C` probability branches are the documented historical exception. Their retail
numeric targets were left unchanged in v1.2 even though earlier translated commands moved the
intended destinations. That omission is reproduced deliberately by the v1.2 compiler because the
published v1.2 bytes are the frozen historical baseline; v1.3 subsequently repairs those three
branches semantically by command ordinal.

## Exact build result

With only:

- the verified retail SCRPACK;
- `localization/en/story_dialogue_v12.csv`;
- `localization/en/story_choices_v12.csv`;
- the structural rules in `botsd.storytext`;

the maintained compiler produced:

`1e3208976bb90749598e1d7359cfda51fe7c095cf3db10459265aeb5dd133051`

The generated bytes are byte-for-byte identical to the independently recovered public-v1.2
SCRPACK.

Applying the existing semantic v1.3 maintenance stage to that generated v1.2 component produced:

`4d7e561344917193f9e672515edd5d2ccf576dcb7ed88d2ddc2092773689df26`

The generated bytes are byte-for-byte identical to the SCRPACK extracted from the published v1.3
full PPF.

## Result

The story/script source path is now proven end-to-end:

`exact retail SCRPACK + repository English data -> exact public v1.2 SCRPACK -> exact public v1.3 SCRPACK`

No previous translated SCRPACK, extracted Japanese story dump, or opaque binary delta is required as
a source input for this component.
